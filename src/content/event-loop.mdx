## The idea

Synchronous JavaScript runs on the current call stack. Promise reactions and queueMicrotask callbacks enter the microtask queue. In a browser, a microtask checkpoint drains that queue before the next task is selected. A timer callback cannot interrupt the currently running code.

## Why it matters

First identify synchronous work, then queued microtasks, then timer tasks. This gives you a reliable explanation of why a resolved promise runs before a zero-delay timeout. Rendering opportunities and host scheduling still matter; a timer delay is not a promise of an exact execution time.

## A practical example

```js
console.log("A");
setTimeout(() => console.log("timer"), 0);
Promise.resolve().then(() => console.log("promise"));
queueMicrotask(() => console.log("microtask"));
console.log("B");
// A, B, promise, microtask, timer
```

## Common mistakes

Do not explain every asynchronous callback as one FIFO queue. Distinguish microtasks from tasks and avoid assuming that a timer means a new worker.

## Try it yourself

Add a promise inside the timer and a timer inside a promise. Write the complete order before executing it.
