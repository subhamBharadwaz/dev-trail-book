## The idea

Authentication establishes who is making a request. Authorization decides whether that identity may perform a particular action on a particular resource. A session cookie or token is a mechanism for carrying identity-related state; neither is permission by itself.

## Why it matters

An opaque server-side session and a signed JWT have different revocation and storage trade-offs. A signature does not encrypt token content. OAuth delegates access; OpenID Connect adds identity conventions on top. Prefer established libraries and providers to inventing a protocol.

## A practical example

```ts
async function readEntry(request, entryId) {
  const session = await authenticateRequest(request);
  if (!session) return { status: 401 };
  const entry = await db.entries.findFirst({
    where: { id: entryId, ownerId: session.userId },
  });
  if (!entry) return { status: 404 };
  return { status: 200, data: toEntryView(entry) };
}
```

## Common mistakes

Hiding an edit button is a usability choice, not a permission check. Treat IDs and claimed roles from the browser as untrusted.

## Try it yourself

Create a two-user test: each user can read their own entry but cannot read or edit the other’s entry by changing its ID.
