## The idea

The latest interview question asked whether the journal page’s initial data should come from a Server Component page or a Client Component Effect. For server-owned initial data in an App Router route, the Server Component is usually the natural starting point. Interactive refreshes and browser-only data may still need a client data layer.

## Why it matters

A server read can authenticate, query directly, and return only the fields the UI needs. Calling your own Route Handler from a Server Component adds an HTTP boundary that may be unnecessary. Start independent reads together and choose caching according to freshness and access requirements.

## A practical example

```tsx
export default async function JournalPage() {
  const user = await requireUser();
  const [entries, tags] = await Promise.all([
    getEntriesForUser(user.id),
    getTagsForUser(user.id),
  ]);
  return <JournalView entries={entries} tags={tags} />;
}
// The data functions enforce access and expose a safe view model.
```

## Common mistakes

Do not move an initial read into useEffect merely because one child has a button. Keep data ownership and interaction ownership separate.
