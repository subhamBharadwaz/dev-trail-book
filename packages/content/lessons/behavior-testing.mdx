## The idea

A useful component test checks what someone can do and observe: find a labelled control, enter a value, submit, wait for the relevant state, and recover from a failure. It should not merely repeat the component’s internal implementation.

## Why it matters

Use role and accessible-name queries where possible. Await asynchronous user interactions and wait for the specific expected result rather than sleeping for a fixed time. Mock an external boundary when appropriate, but keep the page’s real state transitions in the test.

## A practical example

```tsx
test("keeps an error visible after a failed save", async () => {
  const user = userEvent.setup();
  render(
    <EntryForm
      save={async () => {
        throw new Error("offline");
      }}
    />,
  );
  await user.type(screen.getByRole("textbox", { name: "Title" }), "Notes");
  await user.click(screen.getByRole("button", { name: "Save" }));
  expect(await screen.findByRole("alert")).toHaveTextContent("Try again");
  expect(screen.getByRole("textbox", { name: "Title" })).toHaveValue("Notes");
});
// The matchers above require the jest-dom Vitest setup.
```

## Common mistakes

An always-passing test is not useful evidence. Assert visible outcomes after the interaction, not simply that render returned.

## Try it yourself

Break the error message, remove the label, and disable retry one at a time. Confirm a relevant test fails for each regression.
