## The idea

Input and output types can differ when a schema transforms a value. z.input describes what the schema accepts at the type level; z.output and z.infer describe the parsed result. Refinements add checks; transforms normalize or convert data.

## Why it matters

Compose focused schemas with pick, omit and extend where appropriate, but make public and writable fields deliberate. optional accepts undefined; nullable accepts null; nullish accepts both. Defaults address undefined input, not every invalid value. Async refinements or transforms require parseAsync or safeParseAsync. Keep database uniqueness and authorization checks separate from local shape validation.

## A practical example

```ts
import * as z from "zod";
const Minutes = z.string().regex(/^\d+$/)
  .transform(Number).pipe(z.number().int().min(1).max(180));
type MinutesInput = z.input<typeof Minutes>; // string
type MinutesOutput = z.output<typeof Minutes>; // number

const Passwords = z.object({
  password: z.string().min(12),
  confirm: z.string(),
}).refine(value => value.password === value.confirm, {
  message: "Passwords must match", path: ["confirm"],
});
const result = Minutes.safeParse("45"); // output is 45, not "45"
```

## Common mistakes

Blind Number coercion accepts surprising inputs such as an empty string becoming zero. z.coerce.boolean() follows JavaScript truthiness, so the string "false" is truthy. Define the accepted wire format explicitly. A refinement cannot guarantee a future database write will remain unique under concurrency.
