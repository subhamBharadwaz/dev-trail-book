## The idea

A tool interface exposes an application capability through a constrained contract. A read-only tool can retrieve allowed information without changing state, but it still needs input validation, authorization, output validation, time limits, and a useful error model.

## Why it matters

Let the application enforce which resources a caller may inspect. Treat instructions embedded in retrieved content as data, not new permissions. Build one bounded read-only tool, with clear pending, success, empty, and failed states.

## A practical example

```ts
const allowed = new Set(["public-topic-index", "public-glossary"]);
async function readCollection(input, user) {
  if (!allowed.has(input.collection)) throw new Error("Unknown collection");
  await authorizeCollectionRead(user, input.collection);
  const response = await fetch(buildAllowedUrl(input.collection), {
    signal: AbortSignal.timeout(5000),
  });
  if (!response.ok) throw new Error("Collection unavailable");
  return validateCollection(await response.json());
}
```

## Common mistakes

Do not turn a collection name into an arbitrary user-supplied fetch URL. Keep the network destination under application control.

## Try it yourself
