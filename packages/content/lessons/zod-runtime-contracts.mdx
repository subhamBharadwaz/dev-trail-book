## The idea

A Zod schema is executable validation. TypeScript checks your code; Zod checks values when code runs. Define a schema once and infer its output type instead of maintaining a separate interface that can drift.

## Why it matters

Use safeParse when invalid input is an expected outcome; it returns a discriminated success result. parse throws on failure. Handle JSON syntax errors separately from schema errors. Bound strings and arrays, validate the whole structure you use, and validate again on the server even when the client already checked the form. These examples use Zod 4 APIs.

## A practical example

```ts
import * as z from "zod";
const NoteInput = z.strictObject({
  title: z.string().trim().min(1).max(200),
  tags: z.array(z.string().min(1).max(40)).max(8),
});
type NoteInput = z.infer<typeof NoteInput>;
function validateNote(raw: unknown) {
  const result = NoteInput.safeParse(raw);
  if (!result.success) {
    return { ok: false as const, issues: result.error.issues };
  }
  return { ok: true as const, data: result.data };
}
```

## Common mistakes

Do not use raw after parsing: transformations such as trim are reflected in result.data. Default z.object strips unknown keys; strictObject rejects them. Neither policy grants access to a resource. Avoid logging complete sensitive payloads in validation errors.

## Try it yourself

Try whitespace-only titles, nine tags, an extra ownerId and a number instead of a title. Explain the issue path for each failure and show only safe field messages in the UI.
