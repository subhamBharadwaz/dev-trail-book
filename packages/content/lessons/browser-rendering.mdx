## The idea

The browser parses HTML into the DOM, builds style information, calculates layout, and paints/composites the result. JavaScript and resource loading can affect when those steps happen. Some changes require layout; others can be handled more cheaply, depending on the element and browser.

## Why it matters

Repeatedly reading geometry after writing layout-affecting styles can force synchronous work. Measure actual behavior in DevTools instead of declaring every animation GPU-accelerated. Keep expensive work off critical interactions and reserve space for content that loads later.

## A practical example

```js
// Read geometry together, then apply writes.
const widths = cards.map((card) => card.getBoundingClientRect().width);
cards.forEach((card, index) => {
  card.style.setProperty("--measured-width", `${widths[index]}px`);
});
// Avoid alternating a geometry read and write in a large loop.
```

## Common mistakes

Do not optimize based on property names alone. Reproduce the slow interaction and inspect the browser trace first.

## Try it yourself

Use the Performance panel to compare an alternating read/write loop with batched reads followed by writes.
