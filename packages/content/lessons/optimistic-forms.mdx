## The idea

An optimistic update shows the expected result before the server confirms it. It works best for operations with a clear, reversible optimistic representation. The final server response remains authoritative, and failure needs a defined recovery path.

## Why it matters

Distinguish initial, pending, success, and error states. Avoid duplicate submissions and preserve user-entered data when retry is possible. Concurrent optimistic writes need stable identities or operation tracking; restoring one old snapshot can accidentally erase another successful change.

## A practical example

```tsx
async function rename(nextTitle) {
  const previous = title;
  setTitle(nextTitle);
  setPending(true);
  setError("");
  try {
    const saved = await saveTitle(nextTitle);
    setTitle(saved.title);
  } catch {
    setTitle(previous);
    setError("Title was not saved. Try again.");
  } finally {
    setPending(false);
  }
}
// This simple snapshot rollback assumes one mutation at a time.
```

## Common mistakes

Optimism is not appropriate for every operation. When the consequence is difficult to undo, confirmation from the server may be the clearer experience.
