## The idea

A frontend design discussion should start with the user task, expected scale, accessibility needs, and constraints. Then describe components, state ownership, data contracts, rendering boundaries, caching, and failure handling. A diagram is useful only when it clarifies those decisions.

## Why it matters

For a search feature, distinguish the draft input from the submitted query and remote results. For chat, distinguish message identity, streaming progress, cancellation, and persisted history. For a dashboard, explain which reads can run independently and how stale data is communicated.

## A practical example

```js
const design = {
  task: "Find a journal entry quickly",
  localState: ["draft query", "keyboard highlight"],
  remoteState: ["result pages", "request status"],
  contract: { input: "query + cursor", output: "items + nextCursor" },
  failures: ["timeout", "permission change", "empty result", "stale response"],
  evidence: ["keyboard task", "latency trace", "failure-path test"],
};
```

## Common mistakes

Do not claim a familiar library solves the requirements without explaining the data flow and the remaining failure modes.
