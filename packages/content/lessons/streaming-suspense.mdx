## The idea

Streaming can progressively send UI while slower server work finishes. A Suspense boundary defines where a fallback is shown and what can be revealed independently. It does not make the underlying data source faster.

## Why it matters

Put a boundary around a meaningful section, such as a slow activity list, rather than wrapping every line. Keep important initial content available early. Measure whether a waterfall is caused by dependent reads, an overly broad boundary, or work started too late.

## A practical example

```tsx
import { Suspense } from "react";
export default function Dashboard() {
  return (
    <main>
      <h1>Your journal</h1>
      <Suspense fallback={<p>Loading activity…</p>}>
        <RecentActivity />
      </Suspense>
    </main>
  );
}
async function RecentActivity() {
  const entries = await getRecentEntriesForCurrentUser();
  return (
    <ul>
      {entries.map((entry) => (
        <li key={entry.id}>{entry.title}</li>
      ))}
    </ul>
  );
}
```

## Common mistakes

Do not claim that any arbitrary Promise inside a browser Effect automatically activates Suspense. Use a supported data integration or framework pattern.

## Try it yourself

Introduce an artificial slow activity read. Confirm that the heading arrives before the list and that failure has a clear fallback.
