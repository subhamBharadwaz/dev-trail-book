## The idea

An idempotent operation has the same intended effect when repeated as when performed once. This does not require identical responses. A create operation may need an application-level idempotency key when callers can retry after timeouts.

## Why it matters

A disabled submit button reduces accidental clicks but does not protect against network retries, multiple clients, or a lost response. Store the key with the request identity and result using a database constraint and appropriate transaction design. A repeated key with a different payload should be rejected, not silently reused.

## A practical example

```ts
// Illustrative service contract, not an in-memory production store.
async function createOnce(userId, key, payload) {
  return db.transaction(async (tx) => {
    const previous = await tx.findRequest(userId, key);
    if (previous) return requireSamePayload(previous, payload);
    const result = await tx.createEntry(userId, payload);
    await tx.saveRequest(userId, key, payload, result);
    return result;
  });
}
// A unique database key handles concurrent attempts; retry that conflict safely.
```

## Common mistakes

The transaction pseudocode still needs a unique constraint and conflict handling to close the concurrent-check race.

## Try it yourself

Simulate a successful write whose response is lost. Retry the same command and verify that only one row exists.
