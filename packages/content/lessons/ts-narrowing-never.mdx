## The idea

Control-flow analysis narrows types after checks. A discriminant makes alternatives explicit; never can enforce exhaustive handling. User-defined predicates and assertion functions are promises to the compiler, so their implementations must actually establish their claims.

## Why it matters

Prefer runtime schemas for complex external objects. Optional properties are not always a reliable discriminant; use a shared required literal. Branded types distinguish structurally identical values such as UserId and NoteId, but a brand is not authorization or validation. Establish the brand only inside a checked constructor or parser.

## A practical example

```ts
type Result<T> = { ok: true; data: T } | { ok: false; error: string };
function assertNever(value: never): never {
  throw new Error("Unhandled variant");
}
type State = { status: "idle" } | { status: "ready"; count: number };
function label(state: State): string {
  switch (state.status) {
    case "idle": return "Ready to start";
    case "ready": return `${state.count} notes`;
    default: return assertNever(state);
  }
}
declare const userIdBrand: unique symbol;
type UserId = string & { readonly [userIdBrand]: true };
```

## Common mistakes

A predicate returning true unconditionally can make unsafe code compile. A branded string cast from untrusted JSON remains untrusted. Keep ownership checks on the server even when IDs have distinct types.

## Try it yourself

Add a failed state and let exhaustiveness identify the missing case. Write a parser that checks an ID format before constructing a branded value; test invalid and empty inputs.

## Interview checkpoint

Explain the example aloud, predict its inferred types, and describe one runtime failure that compilation cannot prevent. Then implement the exercise without using any or an unchecked assertion to bypass the problem.
